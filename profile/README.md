<p>很多人卡在同一个地方：代理地址填进去了，第一次请求也通了，但业务跑起来之后成功率始终上不去，日志里散着一堆超时、502 和证书错误，不知道该先修哪个。这篇按操作顺序走一遍——先确认前提，再落配置，然后专门处理重试，最后补观测。每一步都给出"这一步算完成"的判断标准，照着往下推，通常两个小时能把一条链路跑到可观测、可恢复的状态。</p>

<h2>一、动手之前先确认的三件事</h2>
<p>这三件事没确认就开始改配置，后面多半要返工。花十分钟，省两小时。</p>
<h3>确认出口地址与鉴权方式</h3>
<p>拿到的是 IP 白名单还是用户名密码，决定你在配置里填什么。白名单方式要先在本机固定出口 IP，再让服务商加白；账密方式要注意特殊字符需要 URL 编码，密码里有 @ 或 # 的时候最容易出错。用 curl 带代理参数跑一次最简单的请求，能通再往下走。</p>
<h3>确认目标是否支持该地区</h3>
<p>有些页面在特定地区会返回不同的内容或直接拒绝。先用浏览器手动访问一次，确认这个地区本身能打开，再去排查代理问题。否则你会花很久去修一个并不存在的网络故障。</p>

<h2>二、第一步：把代理参数写进配置文件</h2>
<p>不要用环境变量临时顶上，尤其是团队协作的项目。写进配置文件，让地址、端口、超时、重试次数都可版本管理，换人接手时不用重新猜。</p>
<h3>四个参数先定下来</h3>
<p>连接超时、读取超时、最大重试次数、退避基数。连接超时给 5 到 10 秒，读取超时按业务给 30 到 60 秒，重试次数 3 次封顶，退避基数 1 秒起步。这四个值先定一个保守版本，跑通之后再调优，别一上来就压到极限。</p>
<h3>把凭据从配置文件里拿出来</h3>
<p>代理账密和 API 密钥放环境变量或密钥管理服务，配置文件里只留占位符。这样配置可以进仓库、可以贴给同事看，不会因为一次误传泄露。</p>

<h2>三、第二步：让重试逻辑区分四类异常</h2>
<p>重试写错的表现是：该重试的不重试，不该重试的疯狂重试。后者更伤，因为会把一次小故障放大成一片超时。</p>

<h3>先分类，再决定重不重试</h3>
<p>按下面这张表分四类，每类给不同处理。判断依据是错误码和错误信息，不要只看 HTTP 状态码。</p>
<table><thead><tr><th>异常类型</th><th>典型表现</th><th>处理动作</th><th>退避建议</th></tr></thead><tbody><tr><td>连接类</td><td>连接超时、握手失败</td><td>换出口后重试</td><td>1s、2s、4s</td></tr><tr><td>鉴权类</td><td>407、401</td><td>不重试，先查凭据</td><td>不适用</td></tr><tr><td>限流类</td><td>429、限速提示</td><td>降并发，拉长间隔</td><td>5s 起，指数退避</td></tr><tr><td>服务端类</td><td>500、502、503</td><td>有限重试，最多 3 次</td><td>2s、4s、8s</td></tr></tbody></table>
<h3>重试要换出口，不是原路重放</h3>
<p>连接类失败时，如果在同一出口上重试，大概率还是失败。正确做法是从池里换一条出口再试。这一步需要在代码里区分"重试"和"重连"，很多 SDK 只提供前者，要自己包一层。</p>
<h3>给重试加总量上限</h3>
<p>除了单次重试次数，还要有一个全局上限，比如每分钟最多重试 100 次。否则一个坏目标会让整个池被重试流量占满，其他业务跟着一起慢。</p>

<h2>四、第三步：补齐观测，别等用户反馈</h2>
<p>没有观测的配置等于没有配置。出问题时你至少要知道：是出口挂了、目标变了，还是自己的代码有问题。</p>
<h3>至少记五个字段</h3>
<p>时间、出口标识、目标、耗时、结果（成功／失败原因分类）。出口标识一定要记，否则你无法判断是某条线的问题还是全局问题。日志按天切分，保留两周，排查够用。</p>
<h3>成功率按出口维度统计</h3>
<p>整体成功率会掩盖单条线的问题：十条线里有一条 50% 成功率，整体看起来还有 95%。按出口分组看，异常线会立刻浮出来。这个视图比任何告警都直观。</p>

<h2>五、第一周按天核对三张清单</h2>
<p>上线第一周是最容易暴露问题的窗口，每天花十分钟看三件事就够。</p>
<h3>第一天看错误分布，第三天看延迟曲线</h3>
<p>第一天重点看错误类型的占比，如果鉴权类错误超过 5%，说明配置或凭据有问题，先修再跑量。第三天开始看延迟曲线，重点看是否存在固定时间段的抬升，那通常对应线路拥塞而不是代码问题。</p>
<h3>第七天做一次故障演练</h3>
<p>手动把主出口断开，看业务是否在预期时间内切到备用、告警是否触发、日志是否记录了切换动作。演练不做，真故障时才会发现备用线路根本没配好。</p>

<h2>常见问答</h2>
<h3>代理通了但目标站点一直返回 403，是代理的问题吗？</h3>
<p>答：先排除三件事：请求头是否完整、地区是否匹配、访问频率是否过高。三者都正常还 403，才怀疑出口本身。用同一出口手动访问一次，能打开就说明问题在请求特征而不是线路。</p>
<h3>重试次数设多少合适？</h3>
<p>答：单次请求 3 次封顶，配合指数退避。次数再多，总耗时已经超过用户容忍范围，重试成功的意义不大。更重要的是把失败原因分类，而不是加大重试量。</p>
<h3>动态出口轮换时正在跑的请求会断吗？</h3>
<p>答：取决于轮换方式。按请求轮换不影响已建立的连接，按时长轮换可能在切换瞬间断开长连接。有长连接需求时，选支持会话保持的池，并把粘性时长设在业务耗时之上。</p>
<h3>证书错误要不要直接跳过校验？</h3>
<p>答：不要。跳过校验会掩盖中间人问题，也让后续排查失去依据。正确做法是把 CA 证书装到信任链里，或者换一条链路正常的出口。</p>

<h2>合规提示</h2>
<p>代理的使用需遵守服务商条款与目标平台的服务协议，本文讨论的是工程侧的配置与容错方法，不涉及绕过平台风控或访问限制。</p>
<p>配置文件中不应明文保存凭据，日志中也不应记录完整的鉴权信息，建议做脱敏处理并按最小必要原则保留。</p>
